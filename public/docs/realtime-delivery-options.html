1. 현재 1:N SSE 연결 방식의 문제

연결 수만큼 자원 유지

단말 한 대마다 장기 HTTP 연결, 스트림, socket, send closure, Map entry와 heartbeat timer가 유지됩니다.

단일 장애 지점

현재 Next.js 프로세스가 재시작되거나 장애가 나면 모든 SSE 연결과 메모리의 revision/lastEvent가 함께 사라집니다.

수평 확장 불가

globalThis는 프로세스 간 공유되지 않습니다. /notify와 /events가 다른 인스턴스에 들어가면 이벤트를 전달하지 못합니다.

Fan-out 비용

사업자 단말 N대에 알림을 보내면 한 요청에서 N개의 enqueue()를 동기 순회합니다.

느린 단말과 정리 지연

backpressure 상한이 없고 조용한 네트워크 단절은 서버 cancel 감지가 늦을 수 있어 버퍼·유령 연결이 남을 수 있습니다.

재연결 폭주

장애 후 모든 단말이 고정 2초 뒤 재시도하면 동시에 요청이 몰리는 thundering herd가 발생할 수 있습니다.

2. 개선 방법의 공통 원칙

연결과 상태 분리

SSE/WebSocket 연결은 각 gateway의 로컬 메모리에 두고, revision과 lastEvent는 Redis/DB 같은 공용 저장소로 이동합니다.

서버 간 이벤트 전달

Redis Pub/Sub, stream 또는 broker를 사용해 어느 API 인스턴스가 받은 이벤트도 모든 연결 서버에 전달합니다.

재연결 분산

지수 backoff와 random jitter를 적용해 장애 복구 시 단말 요청이 한 시점에 몰리지 않게 합니다.

실측 기반 용량 계획

동시 단말 수, 허용 지연, 알림 빈도, 단말당 메모리, event-loop lag와 socket 한도를 부하 테스트합니다.

3. 방식 A · SSE 유지 + Pub/Sub + 수평 확장 현재 요구에 1순위

장점
  • 서버→WebView 단방향 요구에 정확히 맞음
  • 브라우저 기본 EventSource 사용
  • 현재 코드와 변경 폭이 가장 작음
  • 여러 gateway로 연결 분산 가능
단점
  • 장기 연결과 gateway 운영은 계속 필요
  • Redis/PubSub, draining, 모니터링 추가
  • 프록시·로드밸런서 SSE 설정 필요

4. 방식 B · 주기적 Polling 지연 허용 시 단순

장점
  • 장기 연결·connection draining 불필요
  • 서버리스와 일반 로드밸런싱에 유리
  • 현재 /state 개념을 재사용 가능
단점
  • poll 간격만큼 화면 전환 지연
  • 단말 수 ÷ 간격만큼 지속적인 요청 발생
  • 10,000대/5초면 평균 약 2,000 RPS

5. 방식 C · MQTT / IoT Broker 대규모 네이티브 단말에 강점

장점
  • 대량 단말과 작은 메시지에 최적화
  • topic 기반 1:N, QoS, retained message 제공
  • 단말별 인증서와 topic ACL 설계 가능
단점
  • WebView는 MQTT over WebSocket 또는 네이티브 브리지 필요
  • broker·인증서·ACL 운영 복잡도
  • 결제단말 앱 수정 권한이 필요할 수 있음

6. 방식 D · WebSocket

장점
  • 단말 ACK, 상태 보고 등 실시간 양방향 통신
  • 커스텀 protocol과 세밀한 연결 제어
단점
  • SSE와 동일하게 장기 연결 N개를 유지
  • 확장 문제를 자동 해결하지 않으며 gateway/PubSub 필요
  • 단방향 화면 전환만 필요하면 복잡성이 증가

7. 방식 E · 관리형 실시간 서비스

장점
  • 연결 인프라, 수평 확장, 장애 대응 부담 감소
  • 빠른 운영 도입과 SLA 선택 가능
단점
  • 사용량 비용과 vendor lock-in
  • 결제 데이터 정책·보안·국외 이전 검토
  • 서비스별 WebView SDK 호환성 확인 필요

9. 현재 프로젝트 권장안

권장: WebView 기반이며 서버→단말 단방향 화면 전환이 핵심인 현재 요구에서는 WebSocket으로 즉시 교체하지 말고, SSE를 유지하면서 Redis/PubSub과 여러 SSE gateway로 확장하는 방식을 우선 검토합니다.
  1. 규모 기준 확정
    최대 동시 단말 수, 사업자당 단말 수, 허용 화면 전환 지연, 알림 빈도를 확정합니다.
  2. 현재 SSE 부하 테스트
    예상 최대치의 2~3배 연결로 메모리, socket, event-loop lag, fan-out 시간을 측정합니다.
  3. 공용 계층 분리
    revision/lastEvent를 Redis로 옮기고 merchant 이벤트를 Pub/Sub으로 배포합니다.
  4. SSE gateway 수평 확장
    연결 상한, abort 정리, shared heartbeat, backpressure, draining을 적용합니다.
  5. 재연결 안전성
    고정 2초 재시도를 지수 backoff + jitter로 교체합니다.
  6. 대안 전환 조건
    5~30초 지연 허용 시 Polling, 네이티브 앱 수정과 수만 대 규모·QoS가 중요하면 MQTT를 재평가합니다.
