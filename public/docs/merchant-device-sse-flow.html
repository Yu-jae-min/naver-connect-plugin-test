1:N SSE 연동 흐름

기존 구현, 변경된 구현, 실행 순서, 상태와 Ref의 역할, 점검 사항을 소스 코드 줄 번호와 함께 설명합니다.

비교 기준: Next.js 저장소의 HEAD 63eae9e와 현재 미커밋 작업 트리. Vue2 연동 파일은 현재 feature/naver-connect-test 브랜치의 코드를 확인했습니다. 줄 번호는 문서 작성 시점의 파일 기준이며 이후 코드 편집으로 달라질 수 있습니다.

용어와 연결 방향 아키텍처 그림 비교 1. 기존 N:N 2. 변경된 1:N 전체 실행 순서 3. 점검 사항 파일 색인

먼저: 여기서 N:N과 1:N이 뜻하는 것

실제 네트워크 방향: Vue2 데스크톱은 SSE를 구독하지 않습니다. Vue2가 실행되는 브라우저는 POST /api/connect/notify로 이벤트를 발생시킵니다. 단말 브라우저/WebView는 new EventSource("/api/connect/events")로 Next.js 서버에 GET을 시작하고, 서버가 검증 후 text/event-stream 응답을 열면 SSE 연결이 성립합니다. 그 열린 응답에 서버가 나중에 이벤트를 추가해 단말로 내립니다. “N:N”과 “1:N”은 물리적인 양방향 SSE 소켓 수가 아니라 누가 발생시킨 알림을 어느 단말 그룹에 전달하는가를 설명하는 말입니다.

기존: 출처 구분 없는 전역 방송

Vue2 A ─POST─┐
Vue2 B ─POST─┼→ 전역 clients → 단말 1, 2, 3, ...
Vue2 C ─POST─┘

모든 요청이 동일한 연결 목록을 순회했습니다. A의 알림이 B의 단말에도 갈 수 있었습니다. “N:N”은 의도한 사업자 관계가 아니라 구분 없는 전역 fan-out에 가까웠습니다.

현재: 사업자 코드로 그룹 선택

Vue2 token → merchant M ─POST─→ M 채널 → 단말 A, B
Vue2 token → merchant K ─POST─→ K 채널 → 단말 C

“1”은 하나의 merchantCode 채널을 뜻합니다. 여러 Vue2 창이 동일한 유효 토큰을 사용하면 같은 채널에 알림을 보낼 수 있으므로 Vue2 창 하나만 허용하는 제약은 없습니다.

용어: deviceSerialNo는 단말이 주장하는 시리얼, merchantCode는 서버가 조회한 소속 사업자 코드, clientId는 열린 SSE 연결을 제거하기 위한 내부 번호, revision은 사업자 채널 안에서 증가하는 이벤트 순서 번호, lastEvent는 재연결 복구용 마지막 이벤트 한 건입니다.

아키텍처 이미지: 무엇이 달라졌나

두 그림은 같은 다섯 단계를 같은 위치에 놓았습니다. 화살표 위 원형 숫자 1 → 5가 실행 순서이고, 화살표 끝이 요청·전송의 도착지입니다. 단말이 SSE를 먼저 구독하고, Vue2의 별도 POST가 서버 허브에 도착하며, 서버가 이미 열린 SSE 응답으로 메시지를 내려보냅니다.

  • 단말 GET 또는 Vue2 POST
  • 서버 내부 등록·방송 호출
  • 기존 전역 전송
  • 현재 사업자별 전송
서버가 메시지를 “내리는” 정확한 지점: /events가 열린 ReadableStream의 controller.enqueue()를 호출하는 send 함수를 허브에 저장합니다. 이후 별도 POST /notify가 들어오면 허브가 해당 채널의 send를 호출합니다. Vue2와 단말 사이에 직접 연결은 없으며, POST 응답과 SSE 응답도 서로 다른 HTTP 요청입니다.

2. 변경된 1:N 관계 구현 상태

핵심은 서로 다른 출처의 입력을 merchantCode로 합치는 것입니다. 단말은 시리얼을 보내고 서버가 소속 사업자를 조회합니다. Vue2는 Bearer 토큰을 보내고 서버가 로그인 사업자를 조회합니다. 두 조회 결과가 같은 문자열일 때 같은 채널에 도달합니다. 

단말 시리얼 A ─┐
단말 시리얼 B ─┼→ mock admin API → merchantCode M → M.clients에 각각 등록
단말 시리얼 C ─┘
Vue2 Bearer token → mock session API → merchantCode M → M.clients만 순회
위 그림의 A/B/C는 자료구조가 지원하는 구조 예시입니다. 현재 mock API가 인정하는 서로 다른 시리얼은 deviceSerialNoMockData 한 개뿐이며 페이지도 그 시리얼을 고정 사용합니다. 현재 코드만으로 서로 다른 실제 단말 세 대가 검증됐다는 뜻은 아닙니다.

현재 줄 값 의미와 변경 시점

12, 131 "connecting" connect()가 새 EventSource 연결을 시작한 상태입니다. 초기 연결뿐 아니라 오류 뒤 재시도 때도 설정합니다. 237줄에서 spinner가 보입니다.
13, 139 "connected" 브라우저 EventSource의 onopen이 호출된 상태입니다. 화면의 “연결됨” 표시에 사용합니다. 이것만으로 단말이 마지막 비즈니스 이벤트를 렌더했음을 뜻하지 않습니다.
14, 154, 180 "error" onerror 또는 watchdog의 45초 무응답 판정 시 설정합니다. 이벤트가 없으면 대기 화면에 “연결 안됨”이 보입니다. watchdog은 같은 콜백에서 곧바로 connect()를 호출하므로 다시 connecting으로 바뀔 수 있습니다.
15, 108, 209 "device-error" 단말 시리얼이 없거나 사전 /state 조회에서 403이면 설정합니다. 245–249줄에서 단말 연결 불가 문구를 표시합니다. 고정 시리얼이 있으므로 현재의 “시리얼 없음” 분기는 보통 실행되지 않습니다.
41 event: ConnectEvent | null 현재 화면에 렌더할 마지막 수락 이벤트입니다. 초기 null이면 대기 화면이고, applyEvent()가 setEvent(next)할 때 결제 화면으로 전환됩니다. 연결 상태와 별도의 값입니다.
42 deviceError: string 단말 식별 실패·미등록 이유를 표시합니다. 상태가 device-error일 때만 화면에 나타납니다.
44 revisionRef = 0 이 페이지 세션에서 받아들인 최대 revision입니다. syncBaseline과 applyEvent가 올립니다. 같은 값 이하의 중복·오래된 이벤트를 버리는 기준이며 setState처럼 단독 렌더를 일으키지 않습니다.
49 hasConnectedOnceRef = false 이 페이지 세션의 첫 onopen을 구분합니다. 첫 연결에서는 과거 lastEvent를 표시하지 않고 baseline만 맞춥니다. 첫 성공 이후 true가 되어 이후 onopen은 catch-up을 수행합니다.
50 lastActivityAtRef = 0 마지막 수신·연결 활동의 밀리초 시각입니다. 초기화 시 현재 시각, onopen, stream.ready, heartbeat, display.changed 수신 때 갱신합니다. watchdog이 현재 시각과의 차이를 검사합니다.
51 sourceRef = null 현재 EventSource 객체를 가리킵니다. 새 연결 전에 이전 객체를 close()하고 effect 정리 때도 닫기 위해 필요합니다. 서버의 실제 연결 제거는 스트림 cancel 감지에 달려 있습니다.
36–37 STALE_CONNECTION_MS = 45000
WATCHDOG_INTERVAL_MS = 10000 		10초마다 검사해 마지막 활동으로부터 45초 초과면 재연결합니다. 15초 heartbeat의 약 세 간격을 무응답 기준으로 잡은 값입니다.

화면 분기 우선순위, 234–265줄: identifying/connecting이면 spinner → device-error면 오류 → 그 외에 event가 있으면 결제 화면 → 이벤트가 없으면 대기 화면입니다. 따라서 과거 이벤트가 이미 있는 상태에서 연결이 error가 되면 결제 화면 분기가 먼저 적용되어 연결 오류 문구가 별도로 보이지 않습니다.

A. 단말 화면이 처음 열릴 때

  1. Home() 첫 렌더에서 status="identifying", event=null, 네 Ref의 초기값이 만들어집니다. 화면에는 spinner가 나옵니다. app/page.tsx 39–51, 237–244
  2. useEffect가 시리얼을 선택합니다. 현재는 WebView 값 대신 고정 mock 시리얼입니다. 98–101
  3. initialize()가 GET /api/connect/state?deviceSerialNo=deviceSerialNoMockData를 보냅니다. 197–205
  4. /state가 mock admin API를 fetch합니다. mock은 merchantCodeMockData를 반환합니다. 서버는 그 채널의 revision/lastEvent를 반환합니다. state/route.ts 19–30
  5. 사전 조회가 403이 아니면 connect()가 status="connecting"으로 바꾸고 EventSource를 엽니다. app/page.tsx 216–217, 124–135
  6. /events는 시리얼을 다시 mock admin API로 확인하고 해당 사업자 채널에 새로운 clientId로 연결을 등록합니다. stream.ready를 즉시 전송하고 15초 heartbeat를 시작합니다. events/route.ts 18–58
  7. EventSource onopen에서 connected로 전환하고 첫 연결이므로 syncBaseline()을 호출합니다. 과거 마지막 이벤트는 표시하지 않고 현재 revision만 기준으로 맞춥니다. app/page.tsx 137–149, 59–77

B. Vue2 버튼을 누를 때

  1. Vue2가 sending=true로 바꾸고 localhost의 /notify에 message와 고정 Bearer 토큰을 보냅니다. NpayConnectSseTest.vue 32–46
  2. 다른 origin 요청이면 브라우저가 먼저 OPTIONS /notify preflight를 수행할 수 있습니다. 서버가 Authorization과 Content-Type을 허용하는 204를 반환합니다. notify/route.ts 6–20
  3. POST /notify는 토큰을 mock session API로 확인해 merchantCodeMockData를 받습니다. 본문에 merchantCode가 있더라도 그 값을 채널 선택에 사용하지 않습니다. 22–27
  4. 허브가 그 사업자 채널의 revision을 증가시키고 새 이벤트를 lastEvent에 저장한 다음 그 채널의 모든 send를 호출합니다. 다른 사업자 채널은 순회하지 않습니다. lib/sseHub.ts 82–102
  5. 단말이 display.changed를 받으면 JSON을 읽습니다. 새 revision이면 ref와 event state를 갱신하고 결제 화면을 렌더합니다. app/page.tsx 169–172, 53–57, 250–255
  6. Vue2는 HTTP 성공 응답을 받으면 “이벤트 전송 완료”를 표시합니다. 이 시점에 각 단말의 수신·렌더 여부를 확인하는 ACK는 없습니다. NpayConnectSseTest.vue 47–52

C. 단말이 잠들었다가 돌아올 때

  1. 서버는 15초마다 heartbeat를 보냅니다. 단말은 마지막 활동 시각을 갱신합니다. events/route.ts 55–58, app/page.tsx 161–172
  2. 10초 주기 검사에서 45초 넘게 아무 신호를 못 받으면 기존 EventSource를 닫고 같은 시리얼로 다시 연결합니다. app/page.tsx 175–183, 124–135
  3. 명시적 onerror이면 2초 뒤 재연결을 예약합니다. 화면이 다시 visible이 되면 watchdog을 즉시 실행하고 열린 연결에는 catch-up도 요청합니다. 151–159, 185–195
  4. 첫 연결 이후의 onopen은 해당 사업자의 /state에서 마지막 이벤트를 받아 현재 revision보다 새로울 때만 적용합니다. 이벤트 여러 건의 순차 재생은 하지 않습니다. 141–149, 79–96, 53–57

높음 실제 서로 다른 단말의 1:N 전달 page.tsx:100–101은 WebView 시리얼 대신 고정값을 사용하고 mock/admin/devices:8–15는 시리얼 하나만 허용합니다. 서로 다른 A/B 시리얼이 같은 merchantCode로 조회되도록 준비한 뒤 두 SSE 연결이 같은 이벤트를 받는지 확인해야 합니다. 현재 여러 브라우저 창 테스트는 여러 연결 테스트이지 여러 단말 시리얼 테스트가 아닙니다.
높음 다른 사업자 격리 sseHub.ts:98–100은 한 채널만 순회하도록 작성됐지만 현재 mock은 사업자 하나만 반환합니다. 사업자 M/K 각각의 시리얼·토큰을 준비해 M 알림이 K 단말로 전송되지 않고 K의 /state revision/lastEvent도 바뀌지 않는지 확인해야 합니다.
높음 실제 인증·소속 API 계약 connectIdentity.ts:14–24와 두 mock API는 실제 세션·어드민 연동이 아닙니다. 반환 필드, 토큰 전달 방식, timeout, 장애 응답, 단말 소속 변경을 정해야 합니다. 시리얼은 등록 식별자이며 단독으로 요청자가 진짜 단말임을 증명하지 못합니다.
높음 다중 서버 인스턴스 sseHub.ts:30–39의 globalThis는 한 Node.js 프로세스의 메모리입니다. /notify와 /events가 다른 인스턴스로 가는 환경에서는 같은 merchantCode라도 전달되지 않을 수 있습니다. 운영 구조에는 공용 상태·Pub/Sub 설계가 필요합니다.
중간 조회 API 장애의 오류 코드 connectIdentity.ts:18–24는 404, 401, 5xx, 네트워크 오류를 모두 null로 바꿉니다. 그 결과 /events와 /state는 403, /notify는 401로 응답할 수 있습니다. 실제 미등록/인증 실패와 일시 장애를 구분하는 정책이 필요합니다.
중간 사전 검사 이후의 403 재시도 page.tsx:197–211은 첫 /state의 403에서만 영구 단말 오류로 멈춥니다. 그 이후 /events의 403이나 단말 소속 변경은 EventSource onerror와 2초 재시도로 이어질 수 있습니다. 재시도 중단 조건을 확인해야 합니다.
중간 최초 baseline 조회와 실시간 이벤트의 순서 page.tsx:137–149는 syncBaseline()을 await하지 않고, syncBaseline:68–73은 조회한 revision을 올립니다. 연결 직후 이벤트와 상태 응답이 엇갈릴 때 새 이벤트를 화면에 보여줄지 기준선으로만 처리할지 시나리오를 테스트해야 합니다.
중간 heartbeat와 연결 정리 events/route.ts:41–47은 enqueue 실패를 잡지만 해당 client를 즉시 삭제하지 않습니다. cancel():60–65 호출이 조용한 단절에서 지연될 수 있어 타이머·연결 항목이 남는지 실제 WebView 화면 on/off로 확인해야 합니다.
중간 메시지 계약과 파싱 notify/route.ts:29–35는 message를 문자열로 검증하지 않고 nullish 값에만 기본 문구를 적용합니다. page.tsx:169–172는 SSE JSON 파싱 오류를 잡지 않습니다. 운영 이벤트 스키마, 길이 제한, 잘못된 payload 처리를 정해야 합니다.
중간 CORS·토큰 취급 notify/route.ts:6–16의 허용 origin은 *이고 Vue2 토큰은 소스 상수입니다. 실제 로그인 토큰 연동과 허용 origin, credential/CSRF 정책을 정해야 합니다. 현재 PoC 토큰을 운영 인증으로 간주하면 안 됩니다.
낮음 revision 유지·복구 범위 sseHub.ts:30–39, 71–80의 값은 프로세스 재시작 시 사라지고, lastEvent는 한 건뿐입니다. 연속 이벤트 전체 재생이나 재시작 후 복구가 요구되는지 확인해야 합니다.
낮음 화면 상태 표시 page.tsx:237–265에서 기존 event가 있으면 status="error"라도 결제 화면이 표시됩니다. 연결 끊김 표시를 결제 화면 위에도 보여줄지 UX 확인이 필요합니다.
낮음 문서와 실행 코드 일치 README.md와 기존 흐름 문서는 WebView 시리얼을 읽는 것으로 설명하지만 실제 page.tsx:100–101은 mock 고정값입니다. 이 문서는 실행 코드 상태를 기준으로 적었습니다.
현재 검증 수준: 저장소 브리프에는 lint, TypeScript, production build 통과가 기록돼 있습니다. 로컬 API 실행은 포트 바인딩 EPERM으로 수행되지 않았고 실제 WebView·다중 단말·다른 사업자 격리 실측은 기록돼 있지 않습니다. 이 문서의 설명은 소스 분석이며, 미실행 시나리오를 성공으로 표시하지 않습니다.
