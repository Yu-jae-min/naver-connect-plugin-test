아키텍처 의사결정 · 2026-09-22

단말 상시 연결 AWS 아키텍처 비교

현재 Next.js 단일 프로세스 SSE PoC의 한계를 기준으로, ① ALB + SSE Gateway + Redis 방식과 ② AWS AppSync Events 방식을 구현·보안·복구·비용 관점에서 비교합니다. 대상은 약 1,000대 이상의 WebView 단말과 특정 단말 타겟 이벤트입니다.

1. 현재 구현된 SSE 연결 방식과 문제점

현재 PoC는 단말이 deviceSerialNo로 Next.js의 /api/connect/events에 연결하고, 서버가 어드민 매핑을 통해 merchantCode를 확인한 뒤 프로세스 메모리의 사업자 채널에 등록합니다. Vue2 요청은 로그인 토큰에서 사업자를 식별하여 같은 채널에 알림을 보냅니다.

프로세스 로컬 상태

globalThis는 인스턴스 간 공유되지 않습니다. /notify와 단말 연결이 다른 서버에 배치되면 이벤트가 도달하지 않습니다.

단일 장애 지점

배포·재시작·장애 시 모든 연결과 메모리의 revision/lastEvent가 함께 사라집니다.

연결 자원 집중

단말 수만큼 socket, stream, client entry가 필요합니다. 단말별 timer까지 두면 event loop와 메모리 부담이 커집니다.

느린 단말과 유령 연결

backpressure 제한이 없고 조용한 네트워크 단절은 서버 정리가 늦어 버퍼와 죽은 연결이 남을 수 있습니다.

재연결 폭주

모든 단말이 고정 2초 뒤 재접속하면 배포나 네트워크 복구 직후 thundering herd가 발생합니다.

불완전한 catch-up

현재 lastEvent 한 건만 복구합니다. 전체 이벤트 이력, ACK, 정확히 한 번 처리는 보장하지 않습니다.

중요: 서버가 1대라는 사실만으로 곧바로 장애가 발생하는 것은 아닙니다. 1,000개 유휴 SSE 연결은 적절한 런타임에서 충분히 처리할 수 있습니다. 문제는 측정된 연결 한도 없이 단일 프로세스·단일 메모리에 모든 책임을 둔 구조와 장애 복구 수단이 없다는 점입니다.

2. 개선 방법 1 · ALB + SSE Gateway + Redis

현재 EventSource 계약을 유지하면서 연결 처리만 전용 gateway로 분리합니다. API가 Redis에 상태를 저장하고 merchant 이벤트를 발행하면 모든 gateway가 이를 구독하고 자신에게 실제 연결된 단말에만 fan-out합니다.

ALB

Application Load Balancer. HTTP/SSE 연결을 정상 gateway에 분산합니다. idle timeout은 heartbeat 간격보다 충분히 길게 설정합니다.

SSE Gateway

EventSource 연결, 로컬 client registry, heartbeat, Redis 구독, fan-out과 연결 정리만 담당하는 전용 서비스입니다.

ECS / Fargate

ECS는 컨테이너 오케스트레이션, Fargate는 EC2 호스트 없이 task의 vCPU·메모리 실행시간만큼 지불하는 실행 방식입니다.

ElastiCache Redis

gateway 간 공용 revision/lastEvent와 Pub/Sub 채널을 제공하는 관리형 Redis입니다.

Pub/Sub

API가 merchant/device 채널에 publish하면 모든 gateway subscriber가 받고, 로컬 연결 중 대상만 전송합니다.

Connection draining

배포할 task가 새 연결을 받지 않게 한 뒤 기존 단말에 재연결 시간을 주고 안전하게 종료하는 절차입니다.

구현 순서

  1. 용량 기준 확정
    최대 동시 단말, 사업자당 단말 수, 이벤트 빈도, 허용 지연 SLO를 정하고 예상치 2~3배로 부하 테스트합니다.
  2. 공용 상태 이전
    revision, lastEvent를 Redis 또는 영속 DB로 옮깁니다. 전체 복구가 필요하면 Redis Streams/DynamoDB 같은 event log를 별도로 둡니다.
  3. Publish 분리
    /notify는 로그인 토큰에서 merchantCode를 추출하고 대상 단말 소유를 확인한 뒤 상태 저장과 Redis publish를 수행합니다.
  4. Gateway 구성
    각 gateway는 Redis를 구독하고 Map<merchantCode, Map<clientId, Client>>에는 자기 task 연결만 보관합니다.
  5. 연결 보호
    task별 최대 연결 수, request.signal 정리, stream desiredSize/queue 상한과 느린 단말 종료 정책을 둡니다.
  6. 타이머 최적화
    단말별 timer 대신 shared/bucketed heartbeat scheduler를 사용합니다. ALB idle timeout과 heartbeat 주기를 함께 검증합니다.
  7. 안전한 재연결
    클라이언트에 exponential backoff + jitter, online/visibility 복귀 재연결과 revision 기반 중복 제거를 적용합니다.
  8. 무중단 배포
    ALB deregistration delay, SIGTERM 처리, readiness 차단, 재연결 유도 순으로 connection draining을 구현합니다.
  9. 관측성
    task별 active connections, reconnect 수, event-loop lag, 메모리, enqueue 실패, fan-out 시간, Redis 지연을 CloudWatch에 기록합니다.

장단점

장점
  • 현재 EventSource와 API 계약을 대부분 유지합니다.
  • 공용 상태와 Pub/Sub으로 여러 gateway를 안전하게 사용합니다.
  • 인프라·프로토콜·데이터 저장 위치를 직접 통제합니다.
  • 단방향 알림 요구에 단순하고 vendor 종속이 상대적으로 낮습니다.
단점
  • gateway 용량 계획, 배포, draining, Redis HA를 직접 운영합니다.
  • 단말마다 연결 하나가 필요하며 연결 자체를 서로 재사용할 수 없습니다.
  • 유휴 상태에서도 최소 2개 task, ALB, Redis 고정비가 발생합니다.
  • 잘못된 heartbeat/backpressure 설정은 메모리와 재연결 폭주 문제를 만들 수 있습니다.

3. 개선 방법 2 · AWS AppSync Events

AWS AppSync Events가 WebSocket 연결 종단과 채널 fan-out을 관리합니다. 단말은 자기 채널을 subscribe하고, Vue2는 기존 백엔드에 요청하며, 백엔드만 IAM 권한으로 대상 채널에 publish합니다. 현재 EventSource는 AppSync Events SDK/WebSocket 클라이언트로 변경해야 합니다.

권장 통신 흐름

  1. 단말 WebView가 window.npayContext.deviceSerialNo를 읽습니다.
  2. 단말은 연결 인증 API에 단말 증명 정보를 보내고, 백엔드는 등록 여부를 확인합니다. 시리얼 문자열만으로 강한 기기 인증이 되지는 않습니다.
  3. 백엔드는 허용 채널, deviceSerialNo, merchantCode, 만료 시간을 포함한 짧은 수명의 인증 정보를 발급합니다.
  4. 단말은 AppSync Events WebSocket에 연결하고 /device/{deviceSerialNo} 채널을 subscribe합니다.
  5. Vue2는 로그인 액세스 토큰과 targetDeviceSerialNo를 백엔드 /api/connect/notify로 전송합니다.
  6. 백엔드는 토큰에서 검증된 merchantCode를 추출하고 대상 단말이 해당 사업자 소유인지 확인합니다. body의 merchantCode는 신뢰하지 않습니다.
  7. 백엔드는 eventId/revision을 DB에 먼저 저장한 뒤 IAM Role로 해당 AppSync 채널에 publish합니다.
  8. AppSync가 그 채널의 모든 유효 연결에 push합니다. 단말은 더 높은 revision만 적용합니다.
  9. 재연결 시 단말은 마지막 revision 이후 상태/이력을 백엔드에서 조회합니다.

인증과 권한

API Key만 사용하면 부족한 이유

공통 API Key는 “이 앱이 접근 가능하다”만 나타낼 뿐, 이 단말이 /device/dev-001만 구독할 수 있음을 증명하지 못합니다. 다른 시리얼을 추측한 구독을 막기 어렵습니다.

권장 구독 권한

AppSync namespace/channel authorization에서 인증 claim의 allowedChannel과 요청 채널이 같은지 검사합니다. subscriber는 subscribe-only, 백엔드는 publish-only로 분리합니다.

Cognito Unauth Role 주의

모든 단말이 같은 unauth role을 받으면 단말별 신원이 생기지 않습니다. 단말별 claim 또는 authorization handler가 추가되어야 합니다.

Publisher 보호

Vue2에 IAM 자격이나 publish 권한을 노출하지 않습니다. 백엔드 실행 Role에 필요한 AppSync publish 권한과 채널 범위만 허용합니다.

재연결·heartbeat·유실 복구

AppSync가 대신하는 것: 장기 WebSocket 종단, 서버 측 heartbeat 인프라, 연결 서버 수평 확장, 채널 routing/fan-out.

애플리케이션이 계속 해야 하는 것: SDK의 종료 감지와 exponential backoff + jitter, foreground/online 복귀, 재구독, revision 중복 제거, 오프라인 기간 catch-up, 필요 시 수신 ACK.

AppSync가 연결을 관리한다고 해서 오프라인 중 발생한 이벤트가 자동 재생되는 것은 아닙니다. 최신 상태 하나만 필요하면 DB에 last state를 저장하고, 순서대로 모두 복구해야 하면 DynamoDB 등으로 event log를 구성합니다. 이벤트에는 최소 eventId, deviceSerialNo, merchantCode, revision, eventType, createdAt을 포함합니다.

장단점

장점
  • 연결 서버, 로드밸런싱, Auto Scaling, gateway 배포 부담을 AWS에 위임합니다.
  • 1,000대 장기 연결과 단말별 채널 타겟팅에 적합합니다.
  • 유휴 연결 규모가 변할 때 자체 gateway보다 운영이 단순합니다.
  • 백엔드 IAM publish와 채널 authorization으로 권한을 분리할 수 있습니다.
단점
  • EventSource를 유지할 수 없고 AppSync Events SDK/WebSocket으로 단말 코드를 변경해야 합니다.
  • 서비스별 protocol, authorization, 가격 모델에 종속됩니다.
  • 재연결·오프라인 복구·ACK는 별도 애플리케이션 설계가 필요합니다.
  • WebView/OS 버전별 SDK 호환성과 장시간 백그라운드 동작을 실제 단말에서 검증해야 합니다.

SSE Gateway를 선택할 때

  • 단말 EventSource 코드를 바꾸기 어렵다.
  • 팀이 ECS/Redis 운영 경험과 관측 체계를 갖췄다.
  • 연결/데이터가 특정 VPC와 자체 인프라에 있어야 한다.
  • 서비스 종속보다 직접 제어가 중요하다.

AppSync Events를 선택할 때

  • 단말 WebSocket/SDK 변경이 가능하다.
  • gateway 운영 인력이 제한적이다.
  • 접속량 변동이 크고 관리형 확장이 중요하다.
  • 채널 authorization과 AWS 종속을 수용할 수 있다.

5. 비용 산정 시 주의사항

아래 금액은 견적이 아닙니다. AWS 가격, 서울 리전 지원/단가, 메시지 크기와 과금 operation 정의가 변할 수 있으므로 출시 전 AWS Pricing Calculator와 최신 AppSync Events 가격표로 검증해야 합니다.

AppSync 연결량 계산 바로잡기

가정월 connection minutes설명
1,000대 × 일 8시간 × 30일14,400,000분1,000 × 8 × 60 × 30; 1,440,000분이 아님
1,000대 × 24시간 × 30일43,200,000분단말 상시 연결 기준

가정 단가가 정말 $0.08 / 1백만 connection minutes라면 각각 약 $1.152, $3.456이지만, 이 단가와 operation 계산 단위가 현재 서울 리전에 실제 적용되는지 반드시 재확인해야 합니다. “월 1,000원 미만”은 검증 전 확정할 수 없습니다.

SSE Gateway 비용식

Fargate = task 수 × vCPU/메모리 시간단가 × 730

ALB = 시간 요금 + LCU

Redis = node 시간단가 × node 수 × 730

CloudWatch, 인터넷 전송, NAT Gateway 시간/GB 비용도 추가됩니다. 특히 NAT는 작은 PoC에서도 큰 비중이 될 수 있습니다.

AppSync Events 비용식

연결 = 단말 수 × 연결 분/월

이벤트 = publish operation + 구독자별 delivery operation

메시지 크기에 따른 operation 배수, 백엔드 API/DB, 로그, 인터넷 전송 비용을 별도로 포함합니다.

자체 SSE의 거친 참고 범위는 소형 PoC(2개 작은 Fargate task + ALB + 작은 Redis)가 월 $120~300, 운영 HA 기준(2~4 task + Multi-AZ Redis + ALB)이 월 $300~900 수준일 수 있습니다. 이는 실제 견적이 아니며 NAT, 전송량, Redis 등급과 부하 테스트 결과에 따라 크게 달라집니다. AppSync는 1,000개 저빈도 연결에서 더 저렴할 가능성이 높지만, 이벤트가 단말당 빈번하거나 payload가 크면 operation/전송 비용을 다시 계산해야 합니다.

6. 최종 결론

현 시점의 권장 판단

신규 운영 구조를 선택할 수 있고 WebView의 연결 코드를 바꿀 수 있다면 AWS AppSync Events를 우선 PoC하는 것이 합리적입니다. 약 1,000대의 장기 연결과 특정 단말 타겟팅은 서비스 목적에 잘 맞고, gateway/Redis/ALB의 상시 운영 부담과 고정비를 줄일 수 있습니다.

단, 채널 이름만 deviceSerialNo로 만들고 공통 API Key를 주는 구조는 운영에 사용하지 않습니다. 단말별 짧은 수명 인증 + 채널 authorization + 백엔드 IAM publish + DB revision/catch-up을 한 묶음으로 구현해야 합니다.

EventSource 호환성이 필수이거나 AppSync 종속을 수용할 수 없다면 개선 방법 1이 안전한 진화 경로입니다. 기존 PoC를 버리지 않고 Redis 공용 상태, Pub/Sub, 전용 gateway, ALB, backpressure, draining을 단계적으로 추가할 수 있습니다.

권장 검증 계획

  1. 요구량 확정
    24시간 접속 여부, 최대 동시 단말, 단말당 이벤트 수, payload 크기, 허용 지연과 유실 허용 여부를 확정합니다.
  2. AppSync 소규모 PoC
    10~30대 실제 WebView에서 인증, 자기 채널 제한, Wi-Fi/5G 전환, background/foreground, 24시간 연결을 확인합니다.
  3. 복구 검증
    오프라인 중 이벤트, 중복 전달, 순서 역전, token 만료와 재발급을 revision/state API로 복구합니다.
  4. 1,000대 부하 시험
    동시 연결, 동시 재접속, targeted publish, 한 채널 다중 세션, 로그/operation 사용량을 측정합니다.
